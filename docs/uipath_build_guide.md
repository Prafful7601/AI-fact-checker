# UiPath Studio Build Guide — Certified Numeric Verification

Read docs/PDD.md (process) and docs/SDD.md (design contract: queue schema,
Config.xlsx, workflow arguments) before building. This guide names the exact
activities to drag into each workflow. Estimated build time for a teammate
familiar with UiPath Studio and the REFramework template: **~2 hours**.

## 0. Project setup (10 min)

1. UiPath Studio → **New Project → Robotic Enterprise Framework**. Name it
   `CertifiedNumericVerification`.
2. Open `Data/Config.xlsx` (generated by the template) and add the settings
   listed in docs/SDD.md §3 to the **Settings** sheet (Name / Value columns).
   Add an **Assets** row only if you plan to use Orchestrator-managed mail
   credentials; otherwise the local Outlook profile is used directly by the
   Send Outlook Mail Message activity.
3. In `Data/Constants`, confirm `MaxRetryNumber` (used by the framework's own
   transaction-level retry, separate from the API-call Retry Scope below).

## 1. Dispatcher — `ReadInput.xaml` (15 min)

Called from `InitAllSettings` → after Orchestrator queue existence check, in
the Dispatcher's `Process.xaml`.

1. **Excel Application Scope** (or **Read Range Workbook** if using the
   modern activity pack, no Excel install required) → File: `Config("ClaimsInputPath")`.
2. Inside it, **Read Range** → Sheet `claims` → output DataTable `dtClaims`.
3. **For Each Row** `row` in `dtClaims`:
   a. **Invoke Workflow File** → `ValidateClaim.xaml`, passing
      `in_ClaimRow = row`, `in_TablesFolderPath = Config("TablesFolderPath")`,
      `in_SeenClaimIds = seenIds` (a `List(Of String)` initialized before the
      loop) — get back `out_IsValid`, `out_ValidationError`.
   b. **If** `out_IsValid`:
      - **Assign** `dictContent = New Dictionary(Of String, Object) From {
        {"ClaimId", row("claim_id").ToString}, {"Claim", row("claim").ToString},
        {"TableFile", row("table_file").ToString},
        {"TablePath", Path.Combine(Config("TablesFolderPath"), row("table_file").ToString)},
        {"Alpha", Convert.ToDouble(Config("Alpha"))} }`
      - **Add Queue Item** → Queue name: `Config("OrchestratorQueueName")`,
        Item Information: `dictContent`, **Reference**: `row("claim_id").ToString`
        (enables Orchestrator's built-in unique-reference duplicate rejection).
   c. **Else** (business exception): **Log Message** (level `Warn`,
      message includes `out_ValidationError`) and **Add Data Row** to a local
      "business exceptions" DataTable that the Dispatcher writes to
      `results/logs/dispatch_exceptions.csv` at the end (**Write CSV**
      activity) for later audit.

## 2. `ValidateClaim.xaml` (10 min)

Standalone workflow, arguments per docs/SDD.md §4.2.

1. **If** `String.IsNullOrWhiteSpace(in_ClaimRow("claim_id").ToString)` →
   invalid, `out_ValidationError = "missing claim_id"`.
2. **Else If** `in_SeenClaimIds.Contains(in_ClaimRow("claim_id").ToString)` →
   invalid, `out_ValidationError = "duplicate claim_id"`.
3. **Else If** `String.IsNullOrWhiteSpace(in_ClaimRow("claim").ToString)` →
   invalid, `out_ValidationError = "empty claim"`.
4. **Else If** `Not File.Exists(Path.Combine(in_TablesFolderPath, in_ClaimRow("table_file").ToString))` →
   invalid, `out_ValidationError = "missing table"`.
5. **Else** → `out_IsValid = True`; **Invoke Method** `in_SeenClaimIds.Add(...)`.

Use a **Flow Decision**-style ladder (If/ElseIf via nested **If** activities)
so exactly one message is produced.

## 3. Performer — `Process.xaml` main loop (5 min, template-provided)

The REFramework template already implements Get Transaction Item → Process →
Set Transaction Status in `Process.xaml`. You only fill in the "process one
item" section:

1. **Get Transaction Item** (template-provided) → `TransactionItem`.
2. **Assign** local variables from `TransactionItem.SpecificContent`:
   `claimId`, `claim`, `tablePath`, `alpha` (use **Deserialize JSON** if the
   SpecificContent needs conversion, or direct dictionary indexing — the
   modern System activity pack lets you index `SpecificContent("ClaimId").ToString` directly).
3. **Invoke Workflow File** → `CallVerifierAPI.xaml`.
4. **Invoke Workflow File** → `RouteResult.xaml`.
5. Based on `out_NeedsReview`: **Invoke Workflow File** →
   `CreateReviewTicket.xaml` then `SendNotification.xaml`; else
   **Set Transaction Status → Successful** with `out_Verdict` as the output.

## 4. `CallVerifierAPI.xaml` (25 min — the core integration)

1. **Retry Scope** activity (UiPath.System.Activities), wrapping everything
   below:
   - **Action** block:
     a. **HTTP Request** activity: Method `POST`, Endpoint
        `in_ApiBaseUrl + "/verify"`, Body (JSON, Content-Type
        `application/json`):
        ```json
        {"claim_id": "[in_ClaimId]", "claim": "[in_Claim]",
         "table_path": "[in_TablePath]", "alpha": [in_Alpha]}
        ```
        Output: `StatusCode` (Int32), `ResponseContent` (String, or bind
        directly to a JObject output if using the WebAPI activity pack).
     b. **If** `StatusCode = 503` **Or** `StatusCode = 500`: **Throw** a
        `System.Exception` (e.g. `New Exception("API system error: " + StatusCode.ToString)`)
        — this is what the Retry Scope's Condition should catch and retry on.
     c. **Else If** `StatusCode = 400` **Or** `StatusCode = 422`: **Throw
        BusinessRuleException** activity (from `UiPath.System.Activities`,
        or the standard `New BusinessRuleException(ResponseContent)` if your
        template predates the dedicated activity) — this must NOT be
        retried; the Retry Scope's Condition should exclude
        `BusinessRuleException` from its retry predicate.
     d. **Else** (`StatusCode = 200`): **Deserialize JSON** → `out_ResponseJson`
        (JObject); done.
   - **Condition**: `TransactionCount <= Convert.ToInt32(Config("ApiRetryCount"))
     AndAlso Not (exception is BusinessRuleException)`.
   - **Retry Interval**: `Convert.ToInt32(Config("ApiRetryBackoffSeconds"))`
     seconds (Retry Scope supports a fixed or expression-based delay).
2. Before the Retry Scope, optionally add a one-time **HTTP Request** to
   `Config("HealthEndpoint")` in the framework's `InitAllApplications.xaml`
   as a pre-flight check — if `llm_available = false` in the health response,
   log a warning that all transactions this run will end up in the review
   queue (the API's uncalibrated/no-key fallback abstains on everything).

## 5. `RouteResult.xaml` (10 min)

1. From `in_ResponseJson`, **Assign**:
   `out_Verdict = in_ResponseJson("verdict").ToString`,
   `out_NeedsReview = Convert.ToBoolean(in_ResponseJson("sent_to_review"))`.
2. **Log Message** (Info): claim id, verdict, agreement_score, reason — one
   line per transaction, matching the correlation key used in
   `results/logs/api.log` (SDD §6).

## 6. `CreateReviewTicket.xaml` (15 min)

1. **Invoke Workflow File** is called only when `out_NeedsReview = True`.
2. If using **Orchestrator Action Center**: **Create Form Task** /
   **Create External Task** activity, with the claim, verdict, agreement
   score and reason as task data, assigned to the queue/user configured for
   `ReviewerEmail`.
3. If not using Action Center: simply generate a `TicketId` (e.g.
   `"TCK-" + Guid.NewGuid().ToString.Substring(0,8)`) and treat
   `results/review_queue.xlsx` (already written by the API) as the ticket
   system of record — this workflow's only job then is to produce
   `out_TicketId` for the notification email to reference.

## 7. `SendNotification.xaml` (15 min)

1. **Send Outlook Mail Message** (or **Send SMTP Mail Message** if not using
   Outlook) activity:
   - To: `in_ReviewerEmail` (from Config).
   - Subject: `"[CNV Review] Claim " + in_ClaimId`.
   - Body: claim text, table file, agreement score, reason, and a note to
     open `results/review_queue.xlsx` (or the Action Center task link) to
     adjudicate.
2. **Assign** `out_Sent = True` after the send activity (wrap in a **Try
   Catch** so a mail failure is logged as a system exception but does not
   fail the whole transaction — the ticket still exists in
   `review_queue.xlsx` even if the email didn't send).

## 8. `Escalate.xaml` (15 min) — separate scheduled job

Build this as its own small REFramework-style process (or a plain sequence
triggered by an Orchestrator Time Trigger, daily):

1. **Read Range Workbook** → `Config("ReviewQueuePath")`, sheet
   `review_queue` → `dtQueue`.
2. **Filter Data Table**: `status = "Pending"` AND
   `created_at < DateTime.Now.AddDays(-Convert.ToInt32(Config("EscalationDays")))`.
3. **If** filtered row count > 0: **Send Outlook Mail Message** to
   `Config("SupervisorEmail")` listing the overdue claim_ids, then
   **Write Range** back to the workbook updating those rows' `status` to
   `Escalated` (so the same rows are not emailed again tomorrow).
4. **Assign** `out_EscalatedCount = filteredTable.Rows.Count`.

## 9. Wiring it together

`Main.xaml` (Performer) → `InitAllSettings` (reads Config.xlsx) →
`InitAllApplications` (health-check ping) → `GetTransactionData` (Get
Transaction Item from `CNV_Claims`) → `Process.xaml` (steps 3-6 above) →
loop until queue empty → `EndProcess`.

## 10. Testing

Run the Dispatcher against `input/claims.xlsx` first — confirm the 4
deliberately-bad rows (missing table, empty claim, malformed CSV target,
duplicate claim_id) land in the business-exception log/queue and not in
`CNV_Claims`. Then run the Performer with the API started
(`uvicorn api.server:app --host 127.0.0.1 --port 8008`) and confirm answered
claims get `Successful` status while low-agreement/UNVERIFIABLE claims appear
in `results/review_queue.xlsx`. Cross-check against docs/test_cases.xlsx.
